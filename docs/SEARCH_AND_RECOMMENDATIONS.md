# Поиск и рекомендательный подбор Barter: спецификация v1

## Источники и уточнение подхода, 2026-09-06

Требование Максима: дальнейший алгоритм основывать на сильных интернет-источниках
и проверять удобство. Ниже первичные источники; продуктовые решения Barter являются
нашей адаптацией, а не доказанной универсальной формулой. Использованы открытые
материалы, закрытое исследование Baymard не изучалось.

| Источник | Основание | Решение для Barter |
|---|---|---|
| [Baymard: типы запросов](https://baymard.com/blog/ecommerce-search-query-types) | Пользователи ищут конкретные товары, типы товаров, характеристики и решения задач | Раздельные контрольные сценарии: точная модель, категория, свойство, задача. Не оценивать поиск только на названиях |
| [Baymard: область поиска](https://baymard.com/blog/search-scope) | Категория в подсказке должна отличаться от текста запроса | Подсказки «Запрос» и «В категории» визуально различимы; выбранная область видна и снимается |
| [Meili: matching strategy](https://www.meilisearch.com/docs/capabilities/full_text_search/how_to/use_matching_strategy) | all сохраняет термы; last допускает их постепенное удаление | Строгий первый проход для моделей; при пустоте предложить понятное расширение. Не считать AND каждого слова конечным решением для естественной речи |
| [Meili: typo tolerance](https://www.meilisearch.com/docs/capabilities/full_text_search/relevancy/typo_tolerance_settings) | Опечатки можно ограничивать по словам, атрибутам и числам | Защитить модели/числа; проверить реальную версию сервера до новых настроек. Numeric typo protection не заменяет отдельную проверку prefix и SQL-границ |
| [Elastic: fuzzy query](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-fuzzy-query) | Нечёткий поиск расширяет термы в пределах edit distance | Ограничивать число вариантов и стоимость; исправления только при сохранении намерения. Это принцип, не решение мигрировать на Elasticsearch |
| [Elastic: rank evaluation](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/search-rank-eval) | Типичные запросы и ручные оценки позволяют измерять порядок и полноту | Фиксированный набор с оценками 0–3; nDCG@10, Recall@20 и отдельная доля ошибок моделей/фильтров |

### Очередь и приёмка на основе источников

1. Составить минимум 60 русскоязычных запросов и отдельную отложенную выборку:
   «айфон 14 pro», «iphone 140», «самсунг s24», «веласипед», «диван для маленькой
   комнаты», «аренда экскаватора», «обмен велосипеда на самокат». Разметить реальные
   или изолированные тестовые объявления, не добавлять фейковые в production.
2. Защитить модель/числа/единицы и явные фильтры. Ноль ошибочных подмен моделей
   и нарушений фильтров на контрольной выборке — наш критерий, не внешний норматив.
3. Разделить точный поиск и помощь при пустоте: показать исправление с возвратом
   к исходному запросу; расширение категории/города только понятным действием.
   Служебные слова и запросы по задаче требуют отдельного разбора, а не вечного AND.
4. Проверять подсказки на телефоне и с клавиатуры: явная категория, сохранение
   набранного текста и фильтров, отмена исправления, отсутствие устаревших ответов.
5. Сравнивать baseline/изменение на одном корпусе: nDCG@10, Recall@20, доля пустых
   ответов, p95 времени ответа. Затем наблюдать успешные контакты и переформулировки;
   один CTR не доказывает удобство. Окно 3000 не считается решением масштабирования.

Это уточнение плана, не реализация перечисленного. 147 unit-тестов текущей ветки
подтверждают отдельные контракты, но не доказывают качество реальной выдачи и
не дают оснований заявлять превосходство над Авито.

## Реализованное дополнение контракта, 2026-09-06

Текущий `GET /listings` принимает `mode=market|barter`, по умолчанию market
(весь каталог, включая объявления с возможностью обмена). Barter добавляет
JSON-фильтр `attributes.isBarter === true` до подсчёта, пагинации и VIP-выборки.
Согласие продавца задаётся boolean в create/update; string/number/null запрещены.
Существующие объявления без признака не становятся обменными автоматически.
Meili для barter пока не используется, поиск идёт через PostgreSQL fallback.
Ответ содержит `appliedMode`, карточки — производный `isBarter`, без сырых attributes.
Web принимает barter-выдачу только при подтверждении режима и пригодности всех
обычных/VIP карточек. Старый API показывает сообщение о необходимости обновления.
Это контракт текущей ветки, не факт production release и не реализация взаимного
matching. Указанные ниже будущие режимы/ранжирование остаются целевой спецификацией.

Дата: 2026-09-05. Статус: проект алгоритма для поэтапной реализации.
Это не описание уже выпущенной системы и не доказанное превосходство над Авито.
Числа ниже являются стартовыми гипотезами и критериями приёмки, а не замерами.

## 1. Цель и границы

Пользователь находит нужную вещь даже с опечаткой, не теряет свои фильтры и
получает объяснимые рекомендации. Для обмена система учитывает желания обеих
сторон. Продажа и обмен используют общий каталог, но разные правила отбора.
Внешние оплаты, Яндекс ID и карты не нужны для первого этапа.

Три независимых сценария:

1. **Поиск:** исполнить явный запрос. «iPhone 14 256 до 50000» не заменяется
   популярным iPhone 15 или чехлом.
2. **Рекомендации:** помочь выбрать, когда строгого запроса нет; показывать
   отдельно от результатов поиска и указывать причину.
3. **Взаимный обмен:** A хочет вещь B и B согласен на вещь A. Просто похожие
   объявления не являются взаимным совпадением.

## 3. Контракт запроса и ответа

Использовать один DTO в API, SSR главной, mobile search, suggestions и load-more.
Ниже целевой контракт; старые параметры сохраняются через явный адаптер.

```ts
type SearchQuery = {
  q: string;                 // исходный текст, до 200 символов
  mode: 'all' | 'sale' | 'barter';
  categoryId?: string;       // валидировать; включать потомков категории
  cityId?: string;           // стабильный ID, не произвольная строка
  minPrice?: number;         // только конечные, >= 0
  maxPrice?: number;
  priceType?: 'total' | 'per_day' | 'per_month' | 'per_service';
  lat?: number; lon?: number; radiusKm?: number;
  attributes?: Record<string, string | number | boolean>;
  sort: 'relevant' | 'new' | 'cheap' | 'expensive' | 'nearby';
  cursor?: string;
  limit?: number;            // 20 по умолчанию, максимум 50
};
```

Для min>max возвращать понятную ошибку, не молча менять местами. Запретить NaN,
Infinity, отрицательный радиус, несуществующую категорию. City ID вводится с
миграцией справочника; до неё нормализовать существующую строку, включая дефисы
Санкт-Петербурга. Город, показанный в шапке, обязан совпадать с реально применённым.
`nearby` без координат предлагает указать город/место, не притворяется релевантной сортировкой.

Ответ: `items`, `appliedFilters`, `queryInterpretation`, `facets`, `nextCursor`,
`total { value, relation: eq|gte }`, `engine: meili|postgres`, `degraded`,
`requestId`, `rankingVersion`, `indexVersion`. Рекомендации отдельным ответом/полем.
`queryInterpretation` хранит original, normalized, correction?, correctionReason,
suggestedFilters. Персональные причины не выдаются другим пользователям.

Источник истины по доступности и правам: PostgreSQL. Перед выдачей сверять
ACTIVE, ограничения видимости, блокировки и реальную доступность. Индекс не
является обходом авторизации. Никогда не включать личные контакты в публичный индекс.

### 3.1. Реализованный входной контракт S1.1 (Draft PR #6)

Дата: 2026-09-05. Реализована только валидация существующего `GET /listings`,
не весь целевой контракт выше. Имена `priceMin`, `priceMax`, `city`, `page`
сохранены для совместимости с текущим web. Новый формат ответа, cityId,
mode, cursor, attributes и исправление опечаток пока не подключены.

| Поле | Допустимое значение |
|---|---|
| q | Строка до 200 символов после NFKC и нормализации пробелов |
| categoryId / city | Строка до 128 / 80 символов; проверка существования категории ещё предстоит |
| sort | relevant, new, cheap, expensive, nearby; по умолчанию relevant |
| priceMin / priceMax | Целое 0…2147483647; min ≤ max |
| lat / lon | Конечные числа −90…90 / −180…180; только вместе |
| radiusKm | Конечное число 1…500; требует lat и lon |
| page / limit | Целое 1…10000 / 1…50; по умолчанию 1 / 20 |

Пустые строковые поля формы считаются отсутствующими, ноль сохраняется.
Числовые параметры допускают десятичную запись; массивы, объекты, NaN,
Infinity, hex и экспоненциальные строки отвергаются. Повторные и неизвестные
параметры возвращают 400, а не исчезают из условий поиска.
`nearby` без координат тоже возвращает 400.

Для перевёрнутых цен ответ содержит code `invalid_price_range`, field `priceMax`;
для неполных координат code `coordinates_required`, field `lat,lon`.
Остальные ошибки используют стандартный ответ Nest ValidationPipe.
Общий клиентский формат ошибок и их отображение ещё предстоит унифицировать.

Проверено 49 тестами DTO и 8 HTTP-тестами контроллера с подменённым сервисом.
Эти тесты не измеряют релевантность и не доказывают соблюдение фильтров внутри
существующего ListingsService. Следующие части S1: строгий порядок выдачи,
геофильтр независимо от сортировки, стабильная пагинация, web-состояния ошибок.

## 4. Нормализация и понимание запроса

1. Сохранить оригинал для поля поиска. NFKC, lower-case для поиска, схлопывание
   пробелов, нормализация ё/е и дефисов. Не ломать числовые модели, единицы и артикулы.
2. Токенизировать; выделить бренды, модели, размеры, объём памяти, состояние,
   тип товара, город и ценовые выражения. Начать со словарей и правил, без LLM
   в критическом пути каждого запроса.
3. Разделить жесткие значения из фильтров и распознанные предложения из текста.
   Явный фильтр всегда приоритетнее вывода алгоритма. «до 50к» → 50000, «256 ГБ»
   → memoryGb=256; неоднозначное значение показать как снимаемый chip.
4. Контекстные синонимы: айфон↔iphone, макбук↔macbook. «Galaxy» является линейкой
   Samsung, а не эквивалентом всех его товаров. «Машина» неоднозначна: запрос
   «стиральная машина» не расширять до авто. «Аренда» не равна «квартира».
5. Транслит/раскладка: генерировать до двух правдоподобных альтернатив. Пример
   `fqajy` → `айфон`; `ghbdtn` не превращать в товар при отсутствии совпадений.
   Оригинал никогда не теряется. Не исправлять смешанную строку целиком.
6. В словаре держать token, frequency, category distribution, alias type,
   updatedAt. Пополнять из модерированных ACTIVE-объявлений, не из спама.

## 5. Опечатки

Meilisearch уже имеет typo tolerance; не повторять нечёткий поиск грубым
перебором всей БД. Стартовый профиль: до 3 букв только точный/prefix, 4–7 букв
одна ошибка, от 8 букв две. Это профиль для оценки, не универсальная константа.
Исправление влияет на место результата: точное совпадение выше исправленного.

Защитить числовые модели/артикулы: `14` не превращать в `15`, `256` в `128`,
`PS5` в `PS4`. Хранить modelKey и структурированные атрибуты как точные фильтры.
Параметр disableOnNumbers использовать только после проверки версии сервера;
независимо от него проверять защищённые сущности на стороне приложения.

Автокоррекция возможна только если кандидат есть в словаре, соответствует
категории, имеет сильный отрыв от второго кандидата и исходная формулировка
не даёт хороших точных результатов. Порог калибровать на размеченном наборе.
Иначе показать «Возможно, вы имели в виду…» без автоматической замены.

Политика скоринга коррекции (предложение): weighted edit distance для вставки,
удаления, замены, перестановки соседних букв; меньший штраф для соседних клавиш.
Эта логика ранжирует подсказки; она не приписывается внутреннему алгоритму Meili.

В UI: «Результаты для “велосипед”. Искать “велосепед”». Кнопка оригинала повторяет
запрос с отключённой автоматической интерпретацией. Нулевые результаты являются
валидным ответом; fallback движка включается при сбое, не при нормальном нуле.

## 6. Получение кандидатов

Жесткие фильтры применяются ко всем источникам: ACTIVE, mode, category subtree,
city/radius, comparable priceType, price range, attributes, исключения владельцев.
Цена без значения не считается нулём; при денежном фильтре она не подходит.
Аренду за сутки не сравнивать с полной ценой продажи без явного выбора пользователя.

Первый выпуск: только lexical Meili + проверка сущностей. До 300 кандидатов
достаточно как старт для rerank первой страницы, но нельзя этим ограничить весь каталог.
Для остальных страниц использовать согласованную пагинацию, не срез нового пула.

Позднее semantic retrieval включается отдельным флагом, после baseline. Он
помогает запросам «что взять для похода», но не заменяет точные модели и цены.
Нужен выбранный русский embedding model, benchmark качества, бюджет памяти,
времени и стоимости; платный сервис без решения владельца не подключать.

При двух независимых списках допустима прикладная weighted RRF:
`fused(d) = sum(weight_source / (60 + rank_source(d)))`.
Это предложенная схема объединения, не утверждение о внутренней формуле Meili.
Не складывать несопоставимые raw TF-IDF, cosine и rankingScore.
Один документ дедуплицируется по ID, обновления сверяются по версии.

## 7. Ранжирование и строгая сортировка

Сначала eligibility, затем intent tier, затем score. Tier 0: все обязательные
сущности совпадают точно; tier 1: только подтверждённые aliases/typos; tier 2:
более широкие альтернативы, отдельный блок. Аксессуар не проходит как телефон
только за счёт совпадения слов в описании.

Для `relevant` внутри одного tier, стартовая формула:

`score = .70 text + .10 attributes + .07 freshness + .05 quality + .04 trust + .04 preference`

Все признаки ограничены [0,1], правила нормализации версионированы. Не min-max
по текущей странице. `text` учитывать заголовок/модель сильнее описания;
`attributes` только по явно заданным запросом свойствам; `freshness` с затуханием,
не обнулять новым редактированием; `quality` полнота/валидные фото; `trust`
сглаженный рейтинг по реальным сделкам; `preference` небольшой ограниченный бонус.
Новый продавец получает нейтральный prior, а не автоматически плохой рейтинг.
Любая формула проходит offline сравнение с простым lexical baseline.

Для `cheap/expensive/new/nearby` порядок задаётся выбранным полем, затем id.
Персонализация, VIP и TOP не пересортировывают его. Отсутствующая цена/координата
обрабатывается явно. Промо позже отдельным помеченным размещением, внутри тех же
фильтров, с частотными лимитами. Платные позиции не включать в organic quality metrics.

## 8. Пагинация, счётчики, фасеты

Строгая сортировка в PostgreSQL: keyset `(sortField, id)` плюс snapshot boundary;
cursor подписан сервером и содержит hash фильтров/режима/сортировки. Чужой или
просроченный cursor возвращает понятную ошибку. Пул в 400 строк убрать.

Relevance: короткоживущая сессия поиска с упорядоченными IDs, версии ранжирования
и индекса, TTL 10 минут как старт. Для продолжения beyond initial pool расширять
тот же retrieval snapshot либо честно ограничить result window и предложить
уточнение. Не обещать полный total при усечённом пуле. Исчезнувшие ACTIVE позиции
пропускать и добирать; не возвращать проданные товары ради заполнения страницы.

На каждом переходе сохранять query, фильтры, scroll и searchSessionId. Смена
фильтра создаёт новую сессию. Дедупликация ID между страницами; API задаёт порядок.
Load-more: отдельные loading/error/retry/end. Ошибка сети не означает «больше нет».

Фасеты считаются для текущего запроса и фильтров. Для выбранной facet-group
можно исключить её собственный фильтр, чтобы показать доступные альтернативы;
правило одинаковое в UI/API. Нельзя считать фасеты по персональным рекомендациям.

## 9. Рекомендации и холодный старт

Профиль интересов хранится по user/anonymous ID с ограниченным сроком хранения.
Просмотр только после видимости карточки или meaningful dwell, не каждый render.
События: impression(position, requestId), open, favorite, startConversation,
proposalSent/Accepted, completed, hide/report. Последние четыре добавляются
вместе с настоящими сценариями, не генерируются фиктивно.

Начальные веса сигналов: view=1, favorite=3, conversation=5, accepted=8,
hide=-5. Это гипотезы; события дедуплицировать по actor/item/day, ограничивать
вес одного автора, отфильтровать ботов и собственные объявления. Dwell хранить
бакетами. Не писать текст сообщений/контакты в аналитический профиль.

`weight(event) = baseWeight × exp(-ln(2) × ageDays / 14)`.
Агрегировать интерес к категориям/атрибутам, устойчивый бюджет и город.
Дать пользователю скрыть вещь/категорию и сбросить персонализацию. Обязательные
фильтры поиска не расслаблять даже при сильном историческом интересе.

Пулы: похожие по атрибутам; история интересов; co-view по разным пользователям;
качественные свежие объявления; кандидаты обмена. При малом трафике co-view
отключён, используется content-based подбор. Новый пользователь: выбранный город,
популярные категории и разнообразные новые вещи; никаких придуманных предпочтений.

Разнообразие: убрать дубли фото/ID, не больше двух объявлений одного продавца
в первых десяти рекомендациях, ограничить похожие позиции. Это относится к
рекомендациям, не нарушает явную сортировку поисковой выдачи. Исследовательские
позиции до 10% в рекомендательной ленте, без принудительного показа нерелевантного.
Причины: «Похоже на сохранённый велосипед», «Подходит к выбранному бюджету».
Причина строится из реального сигнала; при отсутствии данных её не выдумывать.

## 10. Взаимный обмен

Нужные поля: acceptsSale, acceptsBarter, desiredCategoryIds, desiredAttributes,
freeTextWants, estimatedValue, cashPolicy, cashRangeRub { min, max },
meeting/delivery constraints. Оценка стоимости указана владельцем, не гарантируется.
Никакие значения пожеланий не подставляются по умолчанию вместо ответа владельца.

Для A→B считать `fit(wants(A), B)` и B→A симметрично. Жесткие ограничения
в обе стороны обязательны; разные владельцы, ACTIVE, нет блокировки/отказа.
При пустых wishes(B) показывать «можно предложить», а не «взаимный матч».

Пусть d = доплата владельца A владельцу B. Каждый владелец задаёт допустимый
диапазон исходящей доплаты: положительное значение платит, отрицательное получает.
Для A это [aMin,aMax], для B [bMin,bMax]. В координатах A допустимо пересечение
`[max(aMin,-bMax), min(aMax,-bMin)]`; матч только если lower ≤ upper.
Например A готов доплатить 0–5000, B хочет получить 3000–7000: диапазон B
[-7000,-3000], пересечение [3000,5000]. Без денег у обоих [0,0]. Оба требуют
получить минимум 1000: пересечение пусто. Неограниченную границу хранить как
null и обрабатывать явно, не Infinity в JSON. Разность оценок вещей лишь
предлагает d внутри пересечения и не выполняет платёж.

`mutual = sqrt(fitAB × fitBA)`; обе направленные оценки должны пройти порог.
Итог в рамках допустимых пар: `.70 mutual + .15 logistics + .10 valueFit + .05 trust`.
Пороги/веса откалибровать, процент «совпадения» пользователю не обещать как вероятность.
Причины объясняют желания обеих сторон и допустимую доплату.

Предложение хранит снимок вещей/условий и ревизии объявлений; состояния
draft → sent → accepted/rejected/withdrawn/expired → completed с отдельными
подтверждениями сторон. Изменение/продажа вещи инвалидирует старый матч.
Идемпотентность отправки и принятия, запрет двойного активного принятия одной
вещи, транзакция в БД. Несколько вещей и циклы из 3+ участников позже.

## 11. Отказоустойчивость, индекс и наблюдаемость

Обновление БД + outbox в одной транзакции; worker идемпотентно индексирует по
listingId/revision. Удаление, модерация и продажа удаляют/обновляют индекс;
переиндексация в новый индекс с проверкой перед swap. Проверять завершение
Meili tasks, а не только успешный HTTP enqueue. Не запускать полную индексацию
в каждом пользовательском запросе. Периодически сверять counts/версии.

PostgreSQL fallback: подготовленный normalized search document, русский tsvector
для словоформ + GIN, pg_trgm для кандидатов по опечаткам с ограниченным пулом.
Доступность расширения и план EXPLAIN проверить в тестовой БД. Все SQL параметры
передавать безопасно; не строить произвольный SQL/Meili filter из пользовательской строки.
Fallback сохраняет hard filters и сущности, но не обязан идентично воспроизводить
ранжирование Meili. Клиент получает degraded без внутренних адресов/секретов.

Бюджеты как стартовые цели под нагрузочным тестом: suggestions p95≤150 ms,
search p95≤400 ms, recommendations p95≤500 ms; измерять warm/cold отдельно.
Жёсткие deadline и circuit breaker, отмена устаревших запросов в клиенте.
Suggestions debounce 150–250 ms, не показывать устаревший ответ поверх нового.
Кэш ключ: hash фильтров + mode + ranking/index version; личный кэш изолировать.
TTL, invalidation и повторная DB-проверка ACTIVE важнее быстрого показа старого товара.

Метрики: latency, timeout/error/fallback rate, index lag, query zero-rate,
filter violations, duplicate IDs, CTR по позиции, qualified contacts, accepted
exchanges, complaints. Не оптимизировать только CTR: кликбейт тоже даёт клики.

## 12. Проверка качества и сравнение

Первый fixture corpus минимум 300 объявлений, включая дубли, аксессуары, разные
модели/города/цены/статусы и товары без цены. Минимум 100 запросов: 25 точных,
25 с опечатками/раскладкой, 20 с фильтрами/моделями, 15 неоднозначных, 15 нулевых.
Разметка двумя людьми по шкале 0–3, спорные случаи разрешить до оценки.
Train/tuning/test разделить; тестовые запросы не использовать для настройки.

Цели первого релиза: 100% hard-filter compliance; 0 подмен защищённых моделей;
0 дублей в 5 последовательных страницах; Recall@10 для typo-набора ≥90% при
наличии нужного товара; NDCG@10 лучше текущего baseline минимум на 10% относительных
без падения точных запросов. Это цели, результат неизвестен до измерений.

| Контрольный запрос | Ожидаемый инвариант |
|---|---|
| `айфон 14 256 до 50000` | модель 14 и 256 ГБ, цена до 50000; не чехол/не iPhone 15 |
| `велосепед` | велосипед при подтверждённой коррекции, доступен оригинал |
| `fqajy` | предложен айфон, сохранён исходный запрос |
| `стиральная машина` | бытовая техника, не автомобили |
| `ps5` | не PS4; короткая модель защищена |
| `кран 80 т` | грузоподъёмность, не сантехнический кран при явной категории спецтехники |
| `диван`, город Казань, 10000–20000 | все выдаваемые позиции соблюдают оба фильтра |
| дешёвые + страница 2–5 | монотонная цена, нет возвращающихся ID/рекламной перестановки |
| Meili недоступен | фильтры сохранены, degraded=true, нет ложного пустого успеха |
| новая/проданная вещь | обновление в пределах измеренного SLA индекса; проданная не выдаётся |
| A хочет B, B не хочет A | не помечать взаимным совпадением |
| несовместимые интервалы доплаты | не обещать готовую сделку |

«Лучше Авито» проверять отдельно: одинаковые задания/город/категория, ближайшее
время, фиксировать дату, состав доступного каталога и позиции рекламы. Из-за разных
каталогов raw Recall нельзя напрямую сравнить. Сравнивать время до подходящего
объявления, долю успешных задач и слепую оценку уместности доступных результатов.
Не получать чужие закрытые данные и не обходить ограничения сайта. Отчёт с
интервалами неопределённости; A/B собственного поиска только после достаточного
трафика и расчёта мощности. До этого использовать offline набор и usability tests.

## 13. План PR и алгоритм исполнения

1. S1: единый контракт/API-order, исправить rec injection, sort, cursor, retry.
2. S2: canonical query parser, защищённые сущности, контекстные aliases, typo suite.
3. S3: worker/outbox, task monitoring, PG fallback, нагрузочные сценарии.
4. S4: измеренное ранжирование, объяснения и baseline report.
5. S5: отдельные рекомендации, история/сброс/negative feedback, cold-start.
6. S6: поля обмена, взаимный matcher и transactional proposal lifecycle.
7. S7: semantic/co-view после доказанного выигрыша и согласованного бюджета.

```text
search(request, actor):
  validated = validate(request)
  intent = normalize_and_parse(validated.q, protected_entities)
  constraints = resolve_explicit_filters_then_confirmed_intent(validated, intent)
  session = validate_cursor_or_start(constraints, ranking_version)
  candidates = retrieve_with_deadline(intent, constraints, session)
  if engine_failed: candidates = postgres_fallback(intent, constraints)
  eligible = hydrate_and_recheck_visibility_entities_filters(candidates, actor)
  if sort != relevant: ordered = stable_field_sort(eligible, sort, id)
  else: ordered = intent_tiers_then_versioned_score(eligible)
  page = session_page_without_duplicates(ordered)
  return page, applied_filters, correction, facets, cursor, degraded

recommend(actor, explicit_context):
  signals = deduplicated_decayed_events(actor)
  pools = content_candidates(signals, context) + cold_start_candidates(context)
  eligible = enforce_visibility_and_explicit_context(pools)
  return diversify(rank(eligible)), evidence_based_reasons
```

Каждый PR включает fixture regression, contract test API/SSR/mobile, проверку
ошибок/пагинации. Новая модель/миграция не выкатывается в production этой спецификацией.
