# TXT-03: первый срез вариантов характеристик

Одна строка `CategoryAttributeOption` задаёт категорию, ключ поля, сохраняемое
значение и отображаемую подпись. Порядок хранится явно. В `Listing.attributes`
по-прежнему записывается стабильное значение, поэтому существующие объявления
не переписываются миграцией. Стартовое заполнение идемпотентно и не перетирает
отредактированные записи. Для авто загружены только четыре небольших набора:
топливо, коробка передач, тип кузова и привод.

Второй локальный срез добавляет `parentOptionId`: вариант может зависеть от
другого варианта той же категории. API отдаёт `parentFieldKey/parentValue`, форма
показывает подходящих потомков и очищает их при смене родителя. Сервер отклоняет
несогласованную пару, когда справочник наполнен. Структура рассчитана на
марку → модель → поколение, но сами марки/модели/поколения ещё не импортированы.
Перед массовым импортом нужны стабильные значения, включающие путь родителя
(например, `bmw/3-series`), поскольку название модели не уникально у разных
марок. Для тысяч моделей и поколений потребуется выборка по родителю и поиск
на сервере: нынешний endpoint возвращает весь небольшой список категории.

Форма `new` запрашивает варианты по выбранной категории; при недоступном API
показывает прежние локальные варианты. Сервер проверяет новые значения этих
четырёх полей при создании объявления и при явном изменении `attributes`.
Остальные характеристики пока используют старую конфигурацию веб-клиента.
Редакторы существующих объявлений сейчас не предоставляют управление этими
характеристиками. Поля без записи в справочнике не получили новую валидацию.

Это инфраструктурный срез. Отсутствуют наполненные марки/модели/поколения,
полные справочники подвидов товаров, управление определениями полей, применение
той же схемы к фильтрам, поиску и обменному подбору. Не импортировать чужой
каталог без выяснения прав и версии набора данных. Перед расширением нужен
устойчивый источник, схема обновления и правила для уже опубликованных значений.
