# TXT-02: пожелания и доплата

Одно Listing хранит nullable JSON exchangePreferences отдельно от плоских
характеристик товара. Это явные пожелания, не предложение и не сделка.

| Поле | Смысл |
|---|---|
| anyOffer | Готов рассматривать любые предложения, в том числе за пределами выбранных категорий |
| wantedCategoryIds | До 10 уникальных существующих категорий, допускающих обмен; категория собственной вещи не ограничивает выбор |
| wantedDescription | До 500 символов уточнения желаемого предмета; точные значения справочника хранятся в wantedItems |
| wantedItems | Необязательные до 5 конкретных вариантов: categoryId и attributes с 1–10 контролируемыми select-значениями. Любой вариант подходит целиком; внутри варианта все выбранные поля важны. |
| canAddCash | Владелец готов доплатить |
| maxCashRub | Необязательный предел собственной доплаты, целые рубли; null означает обсуждение, 0 не заменяется на null |
| acceptsCash | Владелец готов принять доплату от другой стороны |

При anyOffer=false требуется категория, непустое описание или конкретный вариант.
Предел без canAddCash, отрицательные/дробные суммы, строки вместо boolean,
неизвестные поля, повторы/несуществующие категории отклоняются API.

## Изменение и совместимость

- Миграция добавляет nullable колонку без приписывания пожеланий старым записям.
- Отсутствие exchangePreferences в PATCH сохраняет текущее значение.
- null явно очищает; объект заменяет пожелания после проверки. Исключение для
  старого клиента: пропущенный wantedItems в PATCH сохраняет существующий массив;
  wantedItems: [] явно его очищает. На создании отсутствие ключа не добавляет массив.
- Переключение в продажу сохраняет пожелания для возврата к обмену, но скрывает
  блок в UI. Это не приватные данные: API по-прежнему может вернуть поле.
- Условия нельзя записать ненулевым объектом для режима без обмена.
- Авторство проверяется до изменения. Фото/избранное/id не копируются.
- Web проверяет exchangePreferencesVersion=1, чтобы старый API не отбросил поле
  молча. Ошибка сохраняет заполненную форму.
- Запись wantedItems (включая пустой массив) дополнительно требует
  structuredWishesVersion=1. Продажа без отправки пожеланий не требует этой capability.

## TXT-03: конкретные пожелания

Общие формы создания и двух редакторов используют текущий attribute-schema /
attribute-options. Показываются только select-поля активной схемы, без свободного
ввода в контролируемые значения. Смена категории очищает характеристики,
смена марки очищает модель. Загрузка/ошибка/недоступный вариант блокируют запись,
есть повтор и удаление варианта. Имена полей имеют явные доступные подписи;
публичная сводка загружает названия, при ошибке сохраняет видимые коды значений.
Атрибуция авто-источника и предупреждение о неполноте остаются видимыми.

API проверяет право категории на обмен независимо от категории собственной вещи,
наследует схему ближайшего предка, проверяет активный select, каждое значение
и точного родителя. Модель без марки, чужая модель, неизвестное поле и дубликат
варианта отклоняются. Массивы/числа вместо строк и лишние ключи отклоняются.
Схема хранения не меняется: additive-поле внутри существующего JSON.
Это сохранение предпочтений, не готовое ранжирование или обещание найти обмен.

## Интерфейс и приёмка

Общий ExchangePreferencesField используется в публикации, редакторе объявлений
и редакторе профиля. Условия показываются на подтверждении и публичной странице.
Любые предложения не обнуляют выбранные предпочтительные категории/описание.
При отключении «могу доплатить» числовой предел очищается явно.
Подпись textarea отделена от содержимого и связана через useId/htmlFor:
доступное имя не изменяется после повторного открытия сохранённого текста.

HTTP acceptance использует только изолированную PostgreSQL CI: создание
межкатегорийного пожелания, чтение карточки/моих объявлений, несвязанный PATCH,
неверная категория/сумма/владелец, сохранение при продаже и явная очистка.
Браузерная fixture проверяет заполнение и повторное открытие на пяти ширинах
в двух темах, пятишаговую публикацию на 360/1280 и защиту от старого API.
Итоговые номера CI и статусы публикации фиксируются в HANDOFF.

Не реализованы этим блоком: полный каталог моделей всех типов товаров, ранжирование по пожеланиям,
обязательства по доплате, платежи, предложения/подтверждённые сделки и история.
Физический iPhone, РФ без VPN и запись реальных объявлений в production не
проверяются изолированными сценариями CI.
