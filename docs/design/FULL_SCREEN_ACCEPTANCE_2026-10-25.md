# BARТЕР — полная экранная приёмка и план реализации
Дата: 2026-10-25. База: master c8dca94. Статус: инвентаризация по Next.js App Router, не визуальная приёмка.

## Решение владельца 2026-10-25: ТОЛЬКО НОВЫЙ BARTER

**Жёсткое правило:** старые Barter / Market, сентябрьские концепты и устаревшие навбары исключены из визуальной приёмки. Legacy-код удалять только после анализа зависимостей: функциональность не ломать.

**Порядок источников:** (1) конкретно утверждённые владельцем октябрьские референсы, включая APPROVED_MESSAGES_REFERENCE.md; (2) отдельные макеты docs/design/barter-2026-10/screens/refined-v2/ с исправлением артефактов; (3) VISION_AND_IMPLEMENTATION.md и новые ассеты; (4) новые отдельные референсы после утверждения. concept-v1, initial-overview, UNIFIED_DESIGN_BRIEF.md, старые разделы DESIGN_STANDARD.md и ранний Liquid Glass — только история, НЕ визуальные эталоны.

**Workflow:** аудит одного маршрута вместе с модальными окнами и UX состояниями → поиск согласованного нового референса → если отсутствует, создание одного отдельного макета, не коллажа → согласование → внедрение общими компонентами → pixel QA mobile/desktop/light/dark + реальные функциональные тесты и iPhone PWA. Статусы: REFERENCE UNKNOWN, DRAFT, APPROVED, IMPLEMENTED, DEVICE VERIFIED. Никогда не превращать DRAFT в APPROVED автоматически.

**Текущее покрытие:** 10 экранов refined-v2 и отдельно спецификации чатов. Их соответствие конкретным маршрутам и подэкранам ещё необходимо проверить. Первым этапом SHELL/navbar, возврат из Barter Dash и глобальные safe-area; визуально нацеливаться ТОЛЬКО на последний утверждённый navbar.

Дополнительные более конкретные поздние источники: APPROVED_MESSAGES_REFERENCE.md (утверждённые inbox, thread, контакты, фото именно из объявления), а также CLAUDE_V2_VISUAL_ACCEPTANCE.md для отдельного прототипа аналитики и других экранов. При конфликте не откатывать новый дизайн к старому: конкретное последнее согласование владельца имеет приоритет, отличие зафиксировать до реализации. Внешний вид пользовательских семи изображений трактовать как явное подтверждение текущего направления, а не как разрешение менять утверждённую структуру сообщений/общих компонентов.

**Поиск действительно отсутствующих экранов/состояний:** отдельные настройки, мои объявления, заказы/история/отзывы, избранное, поиск без результатов, мастер публикации шаги 2+, аналитика с отдельными деталями, служебные состояния, QR/доставка/онлайн/контакт/подтверждения, разбор жалобы, сообщения inbox, пустые и ошибочные состояния. Для каждой позиции сначала выяснить, нет ли позднего утверждения в документации или приложенных источниках; список *кандидатов на создание*, а не доказательство отсутствия.

### Почему 10 файлов не равны 10 принятым страницам
Это девять основных композиций + альтернативная тема главной; в проекте 23 Next.js страницы, а диалоги/мастера/модалки добавляют неадресуемые подэкраны. Не создавать дубликат уже существующего макета лишь из-за другого URL. Один утверждённый визуальный паттерн может быть переиспользован несколькими маршрутами.

## Порядок и правила
1. Общий фундамент: app shell, нижняя навигация, системные safe areas, скролл, верхние панели, клавиатура, PWA и выход из Barter Dash. Не приписывать дефект игре без воспроизведения и git-blame/проверки CSS.
2. Для каждого экрана и подэкрана сверить существующий утверждённый референс, документацию, текущий снимок и поведение. Если референса нет — создать **отдельный** мобильный и desktop референс с состояниями, согласовать с владельцем **до реализации**.
3. Исправлять пакетами от общего к частному, небольшими PR; не вводить новый дизайн вне утверждённой системы. Никаких изменений production до прохождения проверок и разрешения на выпуск.
4. Приёмка: 1:1 сопоставление визуального снимка с утвержденным референсом (пояснять неизбежные различия реальных данных), сценарные тесты с двумя аккаунтами, light/dark, 360/390/393/430 px, desktop, физический iPhone Safari и Home Screen PWA. Проверять скролл, клавиатуру, фокус, геометрию кнопок, реальные API и пустые/загружаемые/ошибочные состояния.
5. Отдельно устранить красный dependency-security-audit для коммита c8dca94, обновить безопасно с регрессионными тестами. Не считать исправленным до зелёного workflow.
6. После полного UX и функциональной приёмки — расширение каталогов и новые интеграции, кроме обязательных для безопасности, доверия и публичного запуска.

## Диагностика навигации — условия завершения
- Изучить root layout, route-specific layouts и стили из игры: body/html overflow, position fixed/sticky, z-index, inset, viewport-fit, dvh/svh, transform, backdrop-filter, safe-area и cleanup при unmount.
- Отдельно проверить direct load, переход между разделами, открытие/закрытие игры, возвращение назад, background/foreground, Safari и Home Screen, обе темы, появление клавиатуры.
- Создать воспроизводимый тест ошибки и доказать причину, затем исправить **одну общую** реализацию, без route-specific костылей.
- Сопоставить фото/video физического iPhone с эталоном; эмулятор не является окончательной приёмкой.

## Шаблон для каждой единицы интерфейса
ID; URL/путь состояния; screenshot actual mobile / desktop; утвержденный reference link или MISSING; light/dark; UX functional status; visual differences; safe-area/keyboard; data states; screenshot diff; automated tests; physical device QA; approval owner; PR; deployed SHA; final status.

## Незакрытые общие риски
Красный аудит зависимостей; устаревшие правила в DESIGN_STANDARD; открытые PR 35/48/83/84 требуют триажа; полная физическая iPhone/PWA проверка отсутствует в старых актах. Не объявлять визуал готовым до подтверждения пользователем.
