# Barter на одной VM в Яндекс Cloud: подготовка чистого запуска

Этот стек пока **не развёрнут**. Он рассчитан на одну VM с Docker Compose:
Next.js + Nest API + PostgreSQL + Meilisearch + Caddy. Старые данные Render
не импортируются; миграции создают чистую схему, а прикладные справочники
инициализируются при старте API. Старый Render/Vercel остаётся как есть до
отдельного переключения домена.

## Условия до запуска

1. Владелец подтверждает действующий грант Яндекс Cloud и лимит расходов.
   Ресурсы VM, диск и публичный IP могут тарифицироваться после окончания гранта.
   Этот сценарий **не гарантирует нулевой счёт**. Если оплачивать нельзя даже
   после гранта, не создавайте VM; сначала согласуйте отключение/альтернативу.
2. Нужен принадлежащий владельцу домен с возможностью создать A-запись.
   Caddy получает HTTPS-сертификат при доступности портов 80/443 из интернета.
3. Нужен доступ к Яндекс Cloud, квоты и созданная сеть/подсеть. Подберите VM
   с достаточными CPU/RAM/диском под четыре сервиса и сборку двух приложений;
   замерьте потребление и стоимость в консоли до создания. Ограничьте SSH
   своим IP, наружу открывайте только 80/443 и нужный SSH. Порты БД,
   Meilisearch, API и Next.js наружу не публикуются.
4. До приёма реальных пользователей организуйте регулярный backup PostgreSQL
   **и** тома `uploads_data` вне VM, шифрование и проверку восстановления.
   Docker-тома на той же VM не являются резервной копией. Здесь нет HA,
   автоматического offsite-backup и бюджетного ограничителя.

## Запуск на подготовленной VM

Установите Docker Engine и Compose plugin по официальной инструкции для ОС,
получите этот репозиторий на VM. Из корня репозитория:

```bash
cd deploy/yandex
cp .env.example .env
chmod 600 .env
```

Заполните `.env` уникальными длинными случайными секретами. Значение
`POSTGRES_PASSWORD` должно совпадать с паролем в `DATABASE_URL`; при символах
вне URL-safe алфавита пароль в URL кодируется. `SITE_DOMAIN` — только имя
хоста без `https://`. Файл `.env` не коммитить и не пересылать в чат.

После назначения VM публичного IP создайте A-запись домена. Из каталога
`deploy/yandex` выполните:

```bash
docker compose config --quiet
docker compose up --build -d
docker compose ps
docker compose logs --tail=100 api
```

`api` применяет `prisma migrate deploy` до старта; если миграция не удалась,
сервис не должен считаться готовым. Проверяйте `https://<SITE_DOMAIN>/health`
(`ok: true`), `/categories`, главную, публикацию с фото, поиск, регистрацию и
чат по WebSocket с двух аккаунтов. `/health` проверяет процесс и режим хранения,
но **не** выполняет SQL-запрос — отдельно проверьте `docker compose ps` и
логи PostgreSQL/API. Не считайте это приёмкой с российского мобильного
интернета: её надо провести на реальном устройстве и операторе.

Для локальной проверки backup без раскрытия пароля в командной строке:

```bash
docker compose exec -T postgres pg_dump -U barter -Fc barter > barter.dump
docker compose exec -T api sh -c 'test -d uploads && ls uploads'
```

`barter.dump` содержит личные данные, когда появятся пользователи: храните
в защищённом месте, перенесите за пределы VM и проверьте восстановление в
**отдельной тестовой БД**. Аналогично сохраните содержимое `uploads_data`.
Команда выше — разовая диагностическая копия, не настроенный backup.

## Граница переключения

До подтверждения HTTPS, API, фото, Socket.IO, backup/restore и мобильного
сценария не меняйте DNS действующего сайта и не отключайте Render/Vercel.
При чистом старте на новом контуре не будет прежних аккаунтов, объявлений,
чатов и медиа. Если после старта изменятся секреты JWT/БД, существующие
сессии могут сброситься или сервис потеряет доступ к БД. При проблеме с новым
доменом верните прежнюю DNS-запись; это возвращает старый контур, **не**
переносит созданные на новой VM данные обратно. Аналитику TXT-09/10 делаем
после стабилизации инфраструктуры.
