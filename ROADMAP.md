## Начни здесь

1. Прочитай этот файл, верхнюю запись `HANDOFF.md` и `docs/PRODUCT_VISION.md`.
2. Для UI прочитай `docs/DESIGN_STANDARD.md`, для объявления также
   `docs/LISTING_DETAIL_REVIEW.md`.
3. Проверь текущие master, открытые PR, локальную ветку и незакоммиченные изменения.
   Этот снимок не заменяет проверку актуального состояния GitHub.
4. Если Максим пишет «продолжаем», бери первый незакрытый пункт следующего раздела.
   Не начинай новый редизайн с нуля и не повторяй уже слитые изменения.
5. Если часть проверки требует входа или реального устройства, зафиксируй границу
   и выполняй доступную часть. Не отмечай заблокированную проверку выполненной.

приёмки и оценка оставшегося объёма. Один этап не равен одному сообщению/PR.

## Ограничения и решения, которые нельзя потерять

- Максим хочет цельный дизайн и рабочие кнопки, а не бесконечные мелкие перекраски.
- Apple-подобная плоская база + ограниченное стекло, а не стекло на каждой карточке.
  Сохранять исходный мобильный хаб и его геометрию; не менять бренд самовольно.
- Яндекс ID, новые API карт и платежи не подключать без отдельного сигнала.
  Наличие OAuth-кода или кошелька не доказывает готовую интеграцию.
- Пауза публикаций снята 2026-09-12. Ранее разрешены merge и production-проверка
  при защищённом preview. Это не разрешение отключать защиту, менять доступы
  или выполнять реальные пользовательские операции. Новые указания важнее.
- Preview ранее требовал входа Vercel; локальное рабочее окружение в текущей
  сессии недоступно. Браузерная приёмка теперь запускается в GitHub Actions
  на локальной production-сборке с фикстурами; защита preview не менялась.
- Реальный iPhone и авторизованные действия не проверены полностью.
- Общий deadline 8s ограничивает ожидание API главной, не всё время загрузки
  и не исправляет сам по себе холодный старт сервера.
- Локальная ветка может отличаться от master. Нельзя сбрасывать чужие изменения
  или переносить целиком старый worktree поверх актуального репозитория.

## Как поддерживать этот файл

После каждого законченного рабочего блока:

1. Обновить статус существующего ID, а не добавлять дубликат задачи.
2. Записать результат, PR/commit, выпуск и точные проверки; отдельно ограничения.
3. Назначить один следующий конкретный шаг в разделе «Следующая задача».
4. Добавить краткую запись сверху HANDOFF, при необходимости обновить BACKLOG.
5. Сохранить изменения в GitHub. Наличие файла только в scratch не обеспечивает
   передачу контекста другому чату. Для документационных правок не менять код приложения.

Иерархия: новые указания Максима → PRODUCT_VISION (цель/приоритеты) → ROADMAP
(текущая очередь) → свежий HANDOFF (доказательства/последний шаг) → BACKLOG
(реестр и история). Старые записи «следующий шаг» не переопределяют новую очередь.
DESIGN_STANDARD задаёт визуальные правила, а не очередь разработки.
